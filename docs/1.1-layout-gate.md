## Reproducible diagnostic

`tools/build-layout-gate.ps1` builds a standalone development executable using
the already pinned LLVM-MinGW 20260616 toolchain. Two builds produced SHA-256:

`6690f0e83a69e65f2ff3a369daf4bbc6f2ad5fd14b712c2ed62a3fcade9d81d3`

Default invocation is read-only. `--apply EN|RU` is rejected with error 87 unless
`--confirm-active-desktop` is present. The executable installs no hooks, injects
no input, reads no window text and makes no registry/settings changes.

Samples deliberately distinguish the diagnostic thread's TSF profile and
language, foreground thread HKL, and shell thread HKL. None is labelled as
verified taskbar pixels. `visual_indicator_verified` is always false.

The medium-integrity runner supports an explicitly opted-in bounded live test:
stop installed CapsLang, run the diagnostic, restart the installed application
in `finally`, record the result. It does not replace the installed executable
or modify its startup tasks. A hung owned child is terminated, not a user app.
The runner is not a crash-proof watchdog; killing the runner/host itself is not
a supported acceptance scenario. Reports use CreateNew, so a retry cannot
overwrite evidence from an operation with an unknown outcome.

Example (ordinary PowerShell, from the repository; choose a new report name):

```powershell
.\tools\build-layout-gate.ps1
.\tools\run-layout-gate.ps1 -Executable "$PWD\build\layout-gate\CapsLangLayoutGate.exe" `
  -Report "$PWD\build\layout-gate\observe-new.jsonl" -Seconds 3
# Only during a coordinated active-desktop test:
.\tools\run-layout-gate.ps1 -Executable "$PWD\build\layout-gate\CapsLangLayoutGate.exe" `
  -Report "$PWD\build\layout-gate\apply-new.jsonl" -Mode RU -Seconds 30 -ConfirmActiveDesktop
```

## Interpretation and remaining acceptance

The proposed ordinary-context TSF calls returning S_OK do **not** establish
that a foreign foreground thread has switched. This is a concrete failed
cross-thread observation, not yet an optical measurement or a typing test.
Do not claim the diagnostic's GetActiveProfile result is a global OS profile.

The user confirmed both screens were available and was asked whether PC's
native indicator changed to RU without cursor transfer/click during the test.
The user did not catch the first visual interval; it is explicitly not accepted
as a visual pass or failure. A repeat began at approximately 16:16:32 UTC,
requesting the same RU in four bounded 30-second rounds. During that interval
the user explicitly answered **EN** for PC's native indicator without moving
the mouse there. The diagnostic was then stopped early (only its exact owned
child) so the runner could restore RC1 in finally. Early termination is
intentional, not a spontaneous crash of the candidate.

A third run started at 16:19:29 UTC after the user explicitly confirmed the
baseline NB=RU / PC=EN and asked to start while watching. The user again
confirmed **"remains EN"** during the running test. This removes the missed
observation-window ambiguity. This repeat is recorded separately in
`gate-apply-ru-6690-ready.jsonl`; the previous repeat is
`gate-apply-ru-6690-repeat.jsonl`. Both use the same verified diagnostic EXE.

The native-indicator requirement has therefore failed this proposed mechanism.
Typing acceptance and the ordinary/high-window matrix on both devices remain
unverified and cannot override that failure. Per the approved stop condition,
do not begin the broad refactor, replace RC1, or publish RC2. Reconsider the
Windows application mechanism first; do not replace the native indicator with
a custom one or add synthetic Win+Space as an undisclosed fallback.

nonce only. The normal module has no test mapping or public apply-message
handler: only its private authenticated pipe can deliver a bounded operation.
After authenticating the protected executable/SID/session/elevation, it pins
the kernel-derived server PID and creation time. The host independently pins
the client process. IPC runs on a private worker, UI operations on the host UI
thread, connected with bounded queues. A timer handles owner loss without a
remaining hook. The module code stays pinned until the app exits; updates must
not replace that file. This follows the lifetime constraints of
[GetModuleHandleEx](https://learn.microsoft.com/en-us/windows/win32/api/libloaderapi/nf-libloaderapi-getmodulehandleexw).

The optional `EngineOptions::profileModule` path consumes this module's events
and confirmations instead of the old broker TSF/manual-shortcut time windows.
Own replies and focus baselines do not create intent; local QPC orders delayed
external events relative to newer requests. Module protocol is now v2:
32-byte event, 328-byte report, 56-byte command. UI sample time, not IPC polling,
determines confirmation freshness. Native-picker/focus races in real apps and
all requested Caps/manual combinations are still acceptance work, not proved
by this model/fixture ordering alone.

`profile_assets.*` embeds both architecture modules in one EXE, validates their
PE architecture and SHA-256, and stages protected `modules/<hash>/<name>.dll`
before the installer stops the prior build. Existing files must match; they
are never overwritten. Old resources remain available to previous EXEs on
rollback. Protected staging, failure recovery and rollback still need a live
installation exercise. The x86 module resolves the native installation from
the protected 64-bit HKLM view: Microsoft's
[known-folder table](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid)
explicitly does not support `FOLDERID_ProgramFilesX64` in a WOW64 process.
