## Актуальное состояние: установленная пара и кандидат RC

Ниже сохранена история этапов. Старые утверждения «не установлено» и
«установщика нет» относятся к моментам соответствующих записей.

- На **4ERK-PC и 4ERK-NB** выполнена настоящая нативная установка, затем
  обновление до **1.1.0-rc.1** SHA-256
  `524DACEFC6CABE980B5BF003D727F2AADE47657CF7A117ADA40E386FC7C4949F`.
  Первые четыре транзакции и оба обновления финального кандидата — code=0. Задачи
  Engine=Highest / Broker=Limited работают в интерактивных сессиях текущих
  пользователей, не SYSTEM. На NB завершена миграция 1.0.0 с резервной копией
  и отключением прежнего Run только после успешного запуска.
- Выполнено реальное сопряжение через LAN: сертификат клиента проверен по
  отдельному доверенному RDC-доступу и явно подтверждён. После обновления
  сохранённая пара автоматически переподключилась. На обеих сторонах
  paired=true, network_phase=Active; RU фактически подтверждён на обеих.
  Коды и секреты в журнал не включены. Это не приёмка всех физических сценариев.
- Пользователь сообщил: при некоторых переходах язык обновляется только
  после клика. Диагностика увидела foreground процесса MWB Helper с EN при
  общем RU. PostMessage в его SYSTEM-окно вернул error 5.
- В точной версии MWB `FormHelper.cs`, обработчик 0x407 активирует DotForm;
  0x408 скрывает её. Исправление сохраняет и адресует последнее рабочее окно
  за точкой, не меняет SYSTEM-окно и не переводит фокус. При холодном запуске
  за точкой выбирается доступное окно текущего пользователя в Z-order.
  Устаревшие/неподтверждённые сведения MWB не меняют выбор окна.
  [Исходник Microsoft](https://github.com/microsoft/PowerToys/blob/389b1a3827b2cf577723288df15437490ef0663a/src/modules/MouseWithoutBorders/App/Helper/FormHelper.cs).
- Регрессия на изолированном desktop проверяет выбор прежнего окна, настоящее
  применение RU за «точкой», отсутствие адресного изменения точки и отказ от
  устаревших сведений. Engine integration: **216 проверок, 0 ошибок** в обычном
  процессе. Остальные наборы: core 455, settings 96, recipient 90+18+21, sync 1113,
  reconnect 1032, broker 315, IPC 72, TLS 141, LAN 78, session 17, runtime 23,
  LED worker 18 — 0 ошибок. Повторные тесты приложения после правок установщика:
  **318 проверок, 0 ошибок**. Ни один тест не выдаёт фикстуру за реальный MWB.
- Повышенная регрессия на PC: **215 проверок, 0 ошибок**, exit 0. Medium-клиент
  проходит в повышенный IPC, low-integrity клиент получает отказ 5.
  SHA теста `AC281BA1D4AC258A85BE1ECBE0AC1313D2CDB3C494CA0D08659FE21F6702A5FE`.
- Две последовательные чистые Release-сборки дали одинаковый SHA-256 RC,
  совпадающий с установленными EXE. PE: AMD64, Windows GUI, timestamp=0;
  импортируются системные Windows/UCRT DLL, внешних runtime-пакетов нет.
- На NB обычный `--restart` завершился кодом 0 без UAC; перезапущены обе роли.
  На PC повторная установка и административный возврат предыдущего снимка
  завершились кодом 0. Затем два удаления: оба code=0, EXE выключен, задач=0;
  повторная установка code=0, задач=2. Сохранённая пара восстановилась до Active
  с подтверждённым EN на обоих. Это не тест аварийного обрыва питания в каждом
  шаге транзакции и не публичный пользовательский откат к 1.0.0.
- Пользователь уточнил: после выбора последнего активного устройства каждая
  смена должна применяться на обоих сразу, без перехода мыши. Активный протокол
  отправляет абсолютное обновление второму engine без условия его локальной
  активности. Текущий сеанс подтвердил общий EN, затем общий RU:
  actual=target=shared_target, peer_applied=Yes. Физическая задержка не замерена.
- RDC временно вернул 401 token_expired, затем доступ восстановился. В обоих
  состояниях сама пара CapsLang работала; после восстановления повторно
  прочитаны статусы, совпадение языка, EXE и работа Guard на PC.
- Исправлена гонка запуска: обычный broker ждёт готовности повышенного engine,
  а не отказывает при кратковременном ERROR_NOT_READY. Opt-in тест
  `tests/installed-lifecycle.ps1 -ConfirmActiveDesktopTest` трижды остановил
  установленную пару процессов и запустил **только обычную задачу broker**.
  Engine автоматически стартовал повышенным без UAC, готовность через
  **143 / 94 / 103 мс**, engine_error=0 во всех циклах.
- Локальный журнал предыдущего кандидата RC охватывает **2,27 часа**:
  912 снимков, engine_error=0 и hook_error=0 во всех. Это наблюдение при обычной
  работе, а не подтверждение 100 переходов или контролируемой матрицы сна/lock.
- Самостоятельная защита от заставки продолжает работать на обоих устройствах.
  Новая версия включает совместимый встроенный процесс с тем же singleton;
  старый Guard не останавливался. Сон/экран/автоблокировка не менялись.
- Отдельного Scroll Lock LED на используемой клавиатуре нет. Физическое
  свечение проверить нельзя. Частичный отказ IOCTL виден в статусе; успешная
  запись class endpoint не считается оптической проверкой.

Открытые ворота стабильной версии: повторная живая проверка переходов без клика,
разный порядок MWB/hooks, ручные способы выбора языка, системный диалог и
повышенный терминал, сон/lock/reconnect и 100 реальных переходов в контролируемом прогоне.
Они не закрываются unit-тестами. До этого допускается только prerelease.

## Подтверждённый блокер синхронизации

Прежний observer ошибочно считал служебную инъекцию движения MWB реальной
активностью. Его предикат больше не называется IsDeliveredActivity и не может
использоваться для выбора авторитетного состояния. Подробности и исходники
MWB: [инженерные проверки](1.1-feasibility.md#обнаруженный-дефект-определения-получателя-mwb).

## Реализованные компоненты следующего этапа

Это компоненты разработки, **не интегрированное приложение 1.1**. Основной
`src/capslang.cpp`, установленный EXE, Run-запись и процесс 1.0.0 не изменены.

- `src/core`: согласованное подавление Caps down/up, удержание и Shift;
  абсолютный EN/RU, latest-wins generation, ограниченные повторные попытки,
  отдельные события фокуса/пользователя/пары, блокировка desktop.
- `src/runtime/engine`: настоящий отдельный hook-поток и worker, проверки
  фактического HKL, периодическое обновление hooks без F24, уведомления питания
  и сессии. Ни hook callback, ни новое ядро не вызывают SendInput.
- `src/runtime/local_ipc`: фиксированные Status/SetLayout/RefreshHook/Stop,
  ACL текущего SID, проверка сессии клиента, запрет удалённых клиентов,
  проверка пути/прав сервера клиентом, лимиты сообщений и времени ожидания.
  Установочный код должен передавать защищённый путь Program Files: самого
  установщика пока нет; test-policy явно разрешает свой тестовый EXE.
- `src/network/tls`: взаимный Schannel TLS 1.2, RSA-3072/SHA-256,
  обязательное pinning точного сертификата обеих сторон, ограниченные буферы
  и ожидания. Тесты используют только loopback. Временные собственные CNG-ключи
  удаляются владельцем после теста; доверенные корни и firewall не меняются.
  Хранение собственного сертификата и ключа добавлено 2026-10-04 (ниже).
  Приглашения, постоянная запись пары и сетевой broker ещё не подключены.
  Это не готовая синхронизация двух компьютеров.
- `src/platform/mwb`: read-only источник **кандидатного** routing-признака
  по служебному 4×4 layered окну Helper. Проверяются конкретная версия и
  подпись Microsoft; заголовки окон не читаются. Неопределённость не считается
  локальной активностью. Обычный процесс здесь получает error 5 при проверке
  повышенного Helper; WTS правильно показывает два приложения и один Helper,
  вместо ложного вывода «MWB выключен». Подпись файла Helper отдельно Valid,
  версия 0.101.2362.0. Этот источник пока **не авторитет для синхронизации**.

Команда: `./build.ps1 -RuntimeTestsOnly`.

- Engine/Windows: 96 проверок, включая два настоящих иностранных процесса,

произвольно поздние ответы и ручной Windows selector во время этого интервала

### Продолжение 2026-10-04: хранение и протокол

- `private_store`: user-scoped DPAPI, закрытый DACL пользователя/SYSTEM,
  запись через временный файл и атомарное переименование. Существующий файл
  не заменяется без явного флага. Пустые/слишком большие и повреждённые данные
  отвергаются. Доверенные корни не меняются.
- `Identity`: сертификат и ссылка на CNG-ключ переживают завершение процесса;
  закрытый ключ не экспортируется. Загрузка проверяет соответствие сертификата
  ключу. Неудачная загрузка не удаляет чужой/существующий ключ и допускает повтор.
  Удаление допускает повтор после sharing violation, сертификат инвалидируется.
- `core/sync`: фиксированные сообщения EN/RU, Lamport-счётчик внутри одной
  согласованной сессии, одинаковое разрешение одновременных событий, защита от
  повторов/старых событий/эха. Pending, Applied, Failed, Locked различаются;
  подтвердить Applied с отличающимся фактическим языком нельзя.
- Для reconnect есть **только алгоритм сравнения интервалов давности активности**
  с учётом RTT. Неизвестная/почти одновременная активность требует нового ввода.
  Согласование новой сессии и подключение к настоящему получателю MWB ещё нужны.
- `network/language_channel`: сообщения поверх закреплённого TLS, разбиение
  и объединение TLS-записей, общий лимит времени на получение кадра; чужая
  сессия и неустановленный/пригласительный серверный канал отвергаются.

Подробности формата и оставшихся условий: [sync-protocol.md](sync-protocol.md).
Обычная сборка и установленное приложение по-прежнему 1.0.0.

### Оставшиеся условия

Перед следующей физической проверкой уточнено чтением **только выбранных булевых
настроек**, без вывода ключей: на NB и PC `MoveMouseRelatively=false`,
`BlockScreenSaverOnOtherMachines=true`, `UseService=true`. По
[Event.MouseEvent](https://github.com/microsoft/PowerToys/blob/389b1a3827b2cf577723288df15437490ef0663a/src/modules/MouseWithoutBorders/App/Core/Event.cs#L104)
относительное кодирование удалённого пакета включается только при
MoveMouseRelatively=true. Это новая **гипотеза для текущей конфигурации**, а не
основание уже считать absolute/relative надёжным классификатором: пока нет
живого подтверждения, как именно InputInjector отражает настоящие переданные
движения в Raw Input. Новому probe нужен прогон с тремя раздельными участками:
мышь NB управляет PC, мышь NB снова управляет NB, физическая мышь PC управляет PC.
Обе мыши нельзя трогать одновременно во время этой диагностической проверки.

Встроенная anti-screensaver функция MWB действительно вызывает PokeMyself
(см. Common.SendAwakeBeat/HumanBeingDetected), но она **не отключалась**.
Изменения PowerToys вне согласованного ремонта не подменяют доказательство
получателя. Отдельный CapsLang Screensaver Guard по-прежнему Running на обеих
машинах. NB пока использует процесс 1.0.0 PID 4104 и прежний HKCU Run; на PC
сам переключатель CapsLang всё ещё не установлен. Это подтверждено повторно
после сетевых тестов; user-facing EXE/installer/UI 1.1 остаются работой впереди.

- Подтвердить настоящего получателя MWB при обоих порядках hooks и неоднозначных
  служебных инъекциях; кандидатная видимость Helper не заменяет этот gate.
- Закрыть manual-selector/focus/late-ack сценарии и реальные полные клавишные
  последовательности. Raw Input release теперь подключён (см. ниже), но
  восстановление после реальной потери hook при удержании, в том числе для
  инъецированной клавиатуры MWB, ещё не прошло аппаратную приёмку.
- Подтвердить изолированный LED-worker на используемой физической клавиатуре;
  на PC ранее обнаружены только виртуальные keyboard-устройства, у пользователя

### 2026-10-04: единый broker, приложение разработки и восстановленный RDC

Сетевой worker теперь объединяет сохранённую identity/pair, приглашение,
подтверждение точного fingerprint и повторное соединение. Внутри TLS отдельный
ограниченный preface различает Session / Enroll / ResumeEnrollment. Временный
неподтверждённый клиент не допускается к Session. После потерянного финального
подтверждения сохраняется возможность Resume; существующая пара не заменяется
молча. Один exclusive listener сохраняется между соединениями, чтобы
TIME_WAIT не ломал немедленное переподключение. При отключении пары активное
соединение прекращается, новые подключения не принимаются до нового Invite;
слушающий handle закрывается при Stop. Сетевой runtime отказывает повышенному
процессу ещё до работы с identity/сокетами. Ошибки запуска сохраняются в статусе.

Добавлены `src/app` и отдельная команда `build.ps1 -AppDevOnly`:

- один native GUI EXE в `build/app-dev/CapsLang.exe`, версия **1.1.0-dev**,
  отдельная от старого default build 1.0.0 в `dist`;
- обычный broker опрашивает engine и сетевой worker вне UI/hook;
- окно статуса, создание/ввод приглашения, подтверждение fingerprint,
  отключение пары, обновление hook, остановка и экспорт диагностики;
- отдельный SID/session control pipe с той же проверкой серверного EXE,
  запретом remote/low clients, фиксированным протоколом и лимитом 8 KiB;
  универсальных команд, путей, запуска shell или последовательностей ввода нет;
- явная операция Pairing содержит UI-only код; обычный Status не имеет этих
  полей, JSON/диагностика используют allowlist, а не сериализацию secret-bearing
  объекта. Буферы IPC с приглашениями очищаются после использования;
- журнал только изменений технического состояния, ротация 1 MiB + один backup;
- `--engine` требует повышение и защищённый фиксированный Program Files EXE:

  ожидания broker, чтобы не создать взаимное ожидание.
