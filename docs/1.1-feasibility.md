# CapsLang 1.1: инженерные проверки

Это **не готовая 1.1.0 и не release candidate**. Рабочий EXE, автозапуск,
раскладки Windows и настройки PowerToys не заменяются.

## Отозванный интерактивный probe

Прежний CapsLangProbe имел недопустимое поведение: завершал рабочий CapsLang
и оставлял его выключенным до закрытия диагностического окна. Кроме того,
пользователь вручную выбирал окна, запускал проверки и сохранял отчёты.

Эта реализация удалена. Новый `CapsLangInventory.exe` умеет только читать
сведения об окружении. Он не останавливает процессы, не запрашивает UAC,
не ставит hooks, не переключает раскладки и не пишет индикаторы. Старое
имя EXE больше не используется сборкой. Не запускать оставшиеся старые probe.

## Автоматическая межпроцессная проверка Windows

Разработчик запускает:

```powershell
.\build.ps1 -IntegrationOnly
```

Скрипт собирает `build\integration\windows_layout_integration.exe` и запускает
его с внешним тайм-аутом 30 секунд. Код создаёт отдельный временный desktop,
**никогда не активирует его**, и запускает только собственные тестовые процессы.
Права DESKTOP_SWITCHDESKTOP у тестового handle нет. Нет SendInput, hooks,
записи LED и обращения к окнам рабочего CapsLang. Тестовые дочерние процессы
ограничены Job Object с KILL_ON_JOB_CLOSE.

Проверяется на реальных HWND и потоках Windows, а не на mock API:

- установка точного EN/RU в другом процессе, 20 последовательных смен;
- повторная установка EN без переключения обратно;
- отказ запроса при неверном PID и исчезнувшем HWND;
- успешная доставка сообщения окну, которое отвергает смену языка;
- задержанное применение и чтение фактической раскладки;
- UIPI: отдельный процесс стартует сразу с restricted Low Integrity token,
  его WM_APP и WM_INPUTLANGCHANGEREQUEST блокируются для окна более высокого IL.

Важно: понижение token уже запущенного Win32-процесса не принимается за
воспроизведение UIPI. Проверка читает фактический integrity RID отдельного
процесса и содержит контрольное сообщение.

Для повышенного прогона разработчик один раз запускает через RunAs тот же EXE
с `--elevated-report`. Пользователь подтверждает только UAC; вся проверка
выполняется автоматически. Результат сохраняется рядом с тестовым EXE в
`windows-elevated-results.txt`. Сам тест проверяет, что действительно повышен.
Это проверка собственных elevated Win32-окон, **не приёмка всех приложений**.

## Только чтение: устройства

```powershell
.\build.ps1 -ProbeOnly
.\build\probe\CapsLangInventory.exe --inventory
```

Вывод — JSON Lines: права, наличие EN/RU, результаты открытия устройств и чтения
LED. Без серийных номеров, путей устройств, названий окон и текста ввода.
Успешное чтение не доказывает запись индикатора или физическое свечение.

## Обнаруженный дефект определения получателя MWB

Старый observer считал любой прошедший цепочку hook немаркированный event
активностью. Это неверно: `InputSimulation.SendMouse` (полученный ввод) и
`MoveMouse*` (служебное движение) используют одинаковый путь инъекции;
`Common.PokeMyself` намеренно создаёт служебные движения. MWB пропускает их
через CallNextHookEx при RealData=false.

Источники соответствующего установленной версии commit:

- [InputSimulation.cs](https://github.com/microsoft/PowerToys/blob/389b1a3827b2cf577723288df15437490ef0663a/src/modules/MouseWithoutBorders/App/Class/InputSimulation.cs#L159-L299)
- [InputHook.cs](https://github.com/microsoft/PowerToys/blob/389b1a3827b2cf577723288df15437490ef0663a/src/modules/MouseWithoutBorders/App/Class/InputHook.cs#L205-L220)
- [Common.cs](https://github.com/microsoft/PowerToys/blob/389b1a3827b2cf577723288df15437490ef0663a/src/modules/MouseWithoutBorders/App/Core/Common.cs#L560-L590)

Предикат переименован в `IsUnconsumedInputCandidate`; прямо запрещено считать
его доказательством реальной активности. Тест фиксирует неоднозначность, а не
«подтверждает MWB». Надёжный выбор последнего получателя пока не реализован.

## Открытые условия выпуска

- Проверка проблемного приложения, LED на физической паре, оба порядка hooks,
  настоящие переходы через MWB и сценарии разрыва/блокировки остаются обязательны.
- Без достоверного получателя нельзя заявлять требуемое разрешение конфликта
  после переподключения. Нельзя молча заменить его приоритетом ПК.
- Нет доступа к управлению вторым ПК — это ограничение стенда, не успешный тест.
- Автоматические тесты изолированных процессов не заменяют двухмашинную приёмку.
- Не устанавливать и не публиковать RC/стабильную версию, пока условия не выполнены.

Документация API: [TSF ActivateProfile](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-itfinputprocessorprofilemgr-activateprofile),
[WM_INPUTLANGCHANGEREQUEST](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-inputlangchangerequest).
