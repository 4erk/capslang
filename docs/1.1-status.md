## Подтверждённый блокер синхронизации

Прежний observer ошибочно считал служебную инъекцию движения MWB реальной
активностью. Его предикат больше не называется IsDeliveredActivity и не может
использоваться для выбора авторитетного состояния. Подробности и исходники
MWB: [инженерные проверки](1.1-feasibility.md#обнаруженный-дефект-определения-получателя-mwb).

## Реализованные компоненты следующего этапа

Это компоненты разработки, **не интегрированное приложение 1.1**. Основной
`src/capslang.cpp`, установленный EXE, Run-запись и процесс 1.0.0 не изменены.

- `src/core`: согласованное подавление Caps down/up, удержание и Shift;
  абсолютный EN/RU, latest-wins generation, ограниченные повторные попытки,
  отдельные события фокуса/пользователя/пары, блокировка desktop.
- `src/runtime/engine`: настоящий отдельный hook-поток и worker, проверки
  фактического HKL, периодическое обновление hooks без F24, уведомления питания
  и сессии. Ни hook callback, ни новое ядро не вызывают SendInput.
- `src/runtime/local_ipc`: фиксированные Status/SetLayout/RefreshHook/Stop,
  ACL текущего SID, проверка сессии клиента, запрет удалённых клиентов,
  проверка пути/прав сервера клиентом, лимиты сообщений и времени ожидания.
  Установочный код должен передавать защищённый путь Program Files: самого
  установщика пока нет; test-policy явно разрешает свой тестовый EXE.
- `src/network/tls`: взаимный Schannel TLS 1.2, RSA-3072/SHA-256,
  обязательное pinning точного сертификата обеих сторон, ограниченные буферы
  и ожидания. Тесты используют только loopback. Временные собственные CNG-ключи
  удаляются владельцем после теста; доверенные корни и firewall не меняются.
  Хранение собственного сертификата и ключа добавлено 2026-10-04 (ниже).
  Приглашения, постоянная запись пары и сетевой broker ещё не подключены.
  Это не готовая синхронизация двух компьютеров.
- `src/platform/mwb`: read-only источник **кандидатного** routing-признака
  по служебному 4×4 layered окну Helper. Проверяются конкретная версия и
  подпись Microsoft; заголовки окон не читаются. Неопределённость не считается
  локальной активностью. Обычный процесс здесь получает error 5 при проверке
  повышенного Helper; WTS правильно показывает два приложения и один Helper,
  вместо ложного вывода «MWB выключен». Подпись файла Helper отдельно Valid,
  версия 0.101.2362.0. Этот источник пока **не авторитет для синхронизации**.

произвольно поздние ответы и ручной Windows selector во время этого интервала

### Продолжение 2026-10-04: хранение и протокол

- `private_store`: user-scoped DPAPI, закрытый DACL пользователя/SYSTEM,
  запись через временный файл и атомарное переименование. Существующий файл
  не заменяется без явного флага. Пустые/слишком большие и повреждённые данные
  отвергаются. Доверенные корни не меняются.
- `Identity`: сертификат и ссылка на CNG-ключ переживают завершение процесса;
  закрытый ключ не экспортируется. Загрузка проверяет соответствие сертификата
  ключу. Неудачная загрузка не удаляет чужой/существующий ключ и допускает повтор.
  Удаление допускает повтор после sharing violation, сертификат инвалидируется.
- `core/sync`: фиксированные сообщения EN/RU, Lamport-счётчик внутри одной
  согласованной сессии, одинаковое разрешение одновременных событий, защита от
  повторов/старых событий/эха. Pending, Applied, Failed, Locked различаются;
  подтвердить Applied с отличающимся фактическим языком нельзя.
- Для reconnect есть **только алгоритм сравнения интервалов давности активности**
  с учётом RTT. Неизвестная/почти одновременная активность требует нового ввода.
  Согласование новой сессии и подключение к настоящему получателю MWB ещё нужны.
- `network/language_channel`: сообщения поверх закреплённого TLS, разбиение
  и объединение TLS-записей, общий лимит времени на получение кадра; чужая
  сессия и неустановленный/пригласительный серверный канал отвергаются.

Подробности формата и оставшихся условий: [sync-protocol.md](sync-protocol.md).
Обычная сборка и установленное приложение по-прежнему 1.0.0.

Core 430, sync 1113, IPC 65, TLS/хранение/кадры языка 48 проверок проходят.
Sync дополнительно прошёл Linux ASan/UBSan. Две независимые сборки TLS-теста
совпали побайтно (это не проверка воспроизводимости будущего Release EXE).

**История отказа до исправления TSF ниже.** После двух успешных ранних запусков
воспроизвелись тайм-ауты и отказы. Дополнительная инструментализация установила:

- Создание/активация TSF ThreadMgr при каждом запросе периодически занимали
  2000–2016 мс. Теперь `LayoutApplier` сохраняется на весь срок STA-потока и
  освобождается до CoUninitialize на том же потоке. Прямые 20 переключений
  после этого проходят примерно за 0,3 секунды вместо около 30 секунд.
- После этого engine-набор завершается примерно за 15 секунд. Несколько запусков
  дали **97 проверок, 1 ошибку**: первый быстрый возврат RU → EN. При отказе первое
  тестовое окно всё ещё находится внутри DefWindowProc для предыдущего RU:
  requests=1, changes=0, handling=1, прошло около 1235 мс. HKL уже RU,
  но обработчик предыдущего сообщения ещё не завершён; EN стоит за ним.
  Это локализует задержку, но ещё не доказывает её внутреннюю причину и не
  исправляет поведение произвольного приложения. Лимит применения не ослаблен.
- Лимиты тестов остались прежними. Build теперь сохраняет вывод при тайм-ауте
  и продолжает независимые наборы; наличие любого отказа даёт ненулевой exit.

Последний полный запуск прошёл: core 430/0, sync 1113/0, engine 97/0,
IPC 65/0, TLS 48/0 (проверки/ошибки), exit 0. Между воспроизведением ошибки
и этим успешным запуском логика применения не менялась — поэтому одиночный
зелёный прогон **не считается устранением периодического отказа**.

На тот момент повышенный результат относился к предыдущей реализации;

### Связка ядра и IPC — продолжение 2026-10-04

Пользователь повторно подтвердил: только полный согласованный 1.1, без
промежуточного локального hotfix. Старый автозапуск не заменён. На NB по-прежнему
1.0.0; на PC полноценного CapsLang нет. Screensaver Guard — отдельный помощник,
его наличие не является установкой переключателя или синхронизации.

- `EngineHost` связывает реальное ядро с SID/session-local IPC. Сначала
  резервируется endpoint, затем запускаются hooks; дубликат не меняет ввод.
  Повышенная роль не читает настройки, файлы журнала, сертификаты или сеть.
- Development IPC v2: запрос 48 байт, ответ 96 байт. Добавлены реальные health
  flags и случайный `engineEpoch`. `SetLayoutIfRevision` связывает применение с
  эпохой процесса и `userRevision`, проверяемой непосредственно worker-потоком.
  Старое сетевое решение не может стереть более новый Caps/manual intent.
  Успешное помещение команды в очередь не выдаётся за Applied.
- Новый `core/reconnect.hpp` согласует версии снимков и интервалы возраста
  активности с RTT, а не системные часы. При неопределённости не выбирает
  listener; свежий ввод разрешает конфликт. Proposal проверяется повторно перед
  commit, устаревшие epoch/revision, повторный commit и чужая session отвергаются.
  Это политика, **ещё не работающий сетевой broker и не доказательство маршрута**.
